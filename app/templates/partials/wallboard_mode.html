Fixing the loop here fixes both. Modes (?mode=presentation and ?mode=wallboard): * Presentation / Wallboard / Exit buttons + full-screen toggle * navigation, footer and chrome hidden; content full width * auto-scroll cycle: RUN down (smooth, slow) → HOLD at bottom → INSTANT jump to top → short HOLD → RUN down again … forever * auto-refresh fires ONLY at the top of the cycle, so a reload never interrupts a mid-page read * a live clock, because a wall screen has to prove it is not frozen * any real interaction (wheel/touch/key/click) pauses the cycle; it resumes on its own 3 s after the last interaction ── WHY THIS WAS REWRITTEN ──────────────────────────────────────────────── Batch 231 drove the scroll from a 40 ms setInterval that nudged 2 px and inferred "the end" from whether the last nudge moved. Two problems the user hit on a tall board: 1. it returned to the top with behavior:'smooth'. On a 5 000 px page that animation outlived the hold window, so the next RUN tick fought the still-running smooth-scroll — the board stalled mid-page and looked "stuck / not scrolling". 2. speed was frame-count based (2 px per 40 ms), so it drifted with load and never felt like a steady crawl. This version uses requestAnimationFrame with a time-based delta (constant px/second regardless of frame rate), a tiny 3-state machine, and an INSTANT jump to the top (no smooth animation to fight). Smooth to read on the way down; snappy and reliable on the way back up. COLOUR IS NOT SET HERE.
